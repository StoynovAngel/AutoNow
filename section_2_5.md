# 2.5 Подбор на технологии за имплементация

## 2.5.1 Сървърна страна: Java 21 + Spring Boot 4

За сървърната страна са разгледани три основни алтернативи: Spring Boot (Java), Node.js (Express/NestJS) и Django (Python).

Node.js е подходящ за I/O-интензивни приложения и позволява споделяне на TypeScript код между frontend и backend, но при по-сложна бизнес логика и строга типизация на доменния модел липсват зрялостта и инструментите на JVM екосистемата. Django предоставя бърза разработка и вградена администрация, но Python не е строго типизиран, а ORM-ът е по-слаб при сложни релационни модели.

Spring Boot е избран, защото:

- осигурява вграден Tomcat и автоконфигурация, което ускорява стартирането на проекта;
- Spring Data JPA и MapStruct намаляват boilerplate при работа с релационни данни;
- Spring Security с JWT е зрял и добре документиран стандарт за stateless автентикация;
- Java 21 records и sealed classes намаляват многословността на езика, запазвайки строгата типизация.

## 2.5.2 База данни: PostgreSQL 16 + H2

Разгледани алтернативи: PostgreSQL, MySQL и MongoDB.

MySQL е близка алтернатива, но PostgreSQL превъзхожда при сложни заявки, поддръжка на JSON колони и по-строго спазване на SQL стандарта. MongoDB е подходящ при документно-ориентиран модел, но доменът на AutoNow е силно релационен — поръчки, шофьори, превозни средства и компании са взаимосвързани обекти, при които транзакционната цялост е критична. Релационният модел е по-естествен избор.

H2 е добавен единствено за интеграционните тестове — стартира в паметта, без Docker зависимост, и не манипулира данните на реалната база.

## 2.5.3 Уеб административен панел: React 19 + TypeScript + Vite

Алтернативи: Angular, Vue.js, React.

Angular е opinionated framework с вградена DI система и строга TypeScript интеграция, но носи значително по-голяма сложност и boilerplate за проект от този мащаб. Vue.js е по-лесен за научаване, но екосистемата е по-малка и TypeScript интеграцията е по-слаба в сравнение с React.

React е избран заради компонентния модел, широката екосистема и естествената интеграция с TypeScript. Интерфейсите на frontend директно отразяват Java DTO-тата от backend, което намалява несъответствията между слоевете. Vite е предпочетен пред webpack заради значително по-бързото стартиране на dev сървъра чрез ES модули — при по-голям проект разликата е осезаема.

## 2.5.4 Мобилно приложение: React Native + Expo

Алтернативи: Flutter, React Native, нативна разработка (Swift + Kotlin).

Нативната разработка осигурява максимална производителност, но изисква две отделни кодови бази и два различни технологични стека, което удвоява разходите за разработка и поддръжка. Flutter позволява cross-platform разработка с висока производителност, но използва Dart — език извън останалата технологична база на проекта.

React Native е избран, защото споделя TypeScript и компонентния модел с уеб панела, което позволява преизползване на логика (services, типове) между двете frontend приложения. Expo допълнително опростява разработката, като абстрахира native конфигурациите за iOS и Android и предоставя готови модули (secure store, локализация).

## 2.5.5 CI/CD: GitHub Actions + SonarQube + Renovate Bot

Алтернативи: Jenkins, GitLab CI, GitHub Actions.

Jenkins е зрял инструмент, но изисква собствена инфраструктура и поддръжка. GitLab CI е естествен избор при GitLab хостинг. Тъй като проектът е хостван в GitHub, GitHub Actions е логичен избор — без допълнителна инфраструктура, с YAML конфигурация директно в репозиторито.

Конфигурирани са три независими работни потока: `test.yml` при всеки PR, `build.yml` за верификация на компилацията и `publish-api-docs.yml` за автоматично генериране на OpenAPI спецификацията. SonarQube осигурява статичен анализ при всеки build чрез `sonar-maven-plugin`, а Renovate Bot следи автоматично за нови версии на зависимостите.

## 2.5.6 Деплойване: Railway

Алтернативи: AWS Elastic Beanstalk, Heroku, Render, Railway.

AWS предоставя максимална гъвкавост, но изисква конфигурация на VPC, load balancer и IAM политики — прекомерна сложност за проект от този мащаб. Heroku е опростен PaaS, но безплатният план беше преустановен, а paid tier-ите са скъпи. Render е добра алтернатива, но Railway предоставя по-добра интеграция с GitHub и по-ясен модел на конфигурация.

Railway е избран, защото:

- деплойването се задейства автоматично при всеки push към `main`, без допълнителна конфигурация на pipeline;
- поддържа монорепо структура чрез `rootDirectory` — backend и web frontend се деплойват като отделни услуги от един и същи репозитор (`StoynovAngel/AutoNow`);
- managed PostgreSQL услуга се свързва с backend автоматично чрез Railway private network (`${{Postgres.DATABASE_URL}}`), без да се излага публично;
- `sleepApplication: true` позволява автоматично спиране на неактивни услуги и намалява разходите при демонстрационен деплой.

Проектът е деплойван с три услуги в production среда, регион `europe-west4`:

| Услуга | Описание | Домейн |
|---|---|---|
| `AutoNow` | Spring Boot backend (rootDir: `/backend`) | `autonow-production-6155.up.railway.app` |
| `AutoNow-Web` | React уеб панел (rootDir: `/web`) | `autonow-web-production.up.railway.app` |
| `Postgres` | Managed PostgreSQL 18 с persistent volume | (private network) |

Builder-ът е Railpack V3 с runtime V2 за и двете приложения. Backend получава environment променливи `DB_URL`, `DB_USERNAME`, `DB_PASSWORD` и `CORS_ALLOWED_ORIGINS` от Railway, а уеб панелът - `VITE_API_BASE_URL`.
